80	2	1. Part A — Introduction and Context
81		Digital LEAP is Limkokwing University’s internship process: placing students with host organisations, supervising weekly logbooks, assessing performance and publishing results. Assignment 2 modelled it as seven processes (1.0–7.0), twenty-two use cases (UC1–UC22) and nine data stores (D1–D9). Most coordination still relies on spreadsheets, email attachments and paper, so data is duplicated, traceability is weak and evidence cannot be reconstructed when a result is challenged.
82		This report documents the conversion of that model into a working database and a secure, offline-first web application for students, supervisors, mentors, the LEAP coordinator, management and the administrator. The system stores the placement lifecycle in MariaDB, enforces business rules in PHP and generates placement letters, grade sheets, management reports and CSV extracts.
83	3	1.1 Aim and objectives
84		The aim is a normalised database and architecture that make the process auditable, secure and usable on laboratory hardware. Five objectives follow:
85	23	map D1–D9 to a normalised schema with enforced integrity;
86	23	implement processes 1.0–7.0 and UC1–UC22 behind role-based access control;
87	23	protect personal data through authentication, validation and audit;
88	23	replace manual consolidation with printable and exportable outputs;
89	23	demonstrate the system with Sierra Leone seed data and a repeatable test pass.
90		Success is more than screens. A coordinator must trace a published mark to the logbook weeks, both evaluations and the assessed report; a student must see only their own record; and a supervisor must not reach another company’s students. These constraints shaped the schema and the architecture.

203	3	2.3 Integrity, transactions and indexes
204		InnoDB foreign keys restrict deletion where history matters. Unique keys prevent duplicate accounts, preferences for one organisation and placements for a student in a year. Enumerated statuses and check constraints cover scores, weights and capacity; PHP validation repeats them at the boundary.
205		Placement creation inserts the row, writes the audit event and queues notifications in one transaction. Mark computation reads the logbook average, both evaluations and the report score, then writes the mark and its audit snapshot together. The preference swap uses a temporary rank of zero because uq_app_rank forbids shared ranks.
206		Indexes follow real queries: foreign-key columns for joins, and composites on placement (student_id, academic_year), logbook_entry (placement_id, week_no), evaluation (placement_id, evaluation_type), notification (user_id, read_at) and audit_log (action, created_at).

287	2	3. Part C — Technical Architecture
288		The application must run offline in a computer laboratory on modest laptops and be handed over to another cohort. That rules out a distributed single-page application and a cloud database, and favours server-rendered pages with a minimal dependency footprint.
289	3	3.1 Architectural drivers
290		Five drivers shaped the architecture: offline operation; low bandwidth, favouring server-rendered HTML; security, requiring one entry point for sessions, CSRF and authorisation; maintainability, requiring a layout a student can learn in a week; and auditability, requiring all state changes to pass through one layer.
291	3	3.2 Three-tier structure
292		Figure 1 shows the three tiers. The presentation tier is HTML5 and CSS rendered by PHP, with one small JavaScript file handling confirmations through data attributes; no inline script or style is allowed, which keeps the content security policy strict. The application tier holds the front controller, router, controllers, services and views. The data tier is MariaDB with twenty-four InnoDB tables. Security is cross-cutting.
293		
294		Figure 1: Three-tier architecture with cross-cutting security
295		Controllers read input, call services and select a view. Services own rules that must not be duplicated: Guard decides access, Csrf verifies tokens, Upload validates files, Notify writes notifications and mail together, Mailer delivers queued messages, Settings supplies configuration and Audit records changes. Views escape every value through e().
296	3	3.3 Request lifecycle
297		Every request enters index.php, which loads bootstrap: base paths, autoloader, configuration, storage directories, security headers and a hardened session. Bootstrap checks timeouts, rejects POST requests without a valid CSRF token with HTTP 419 sent as an explicit status line, enforces the forced password change gate and dispatches the route. The router resolves “METHOD route” to a controller, method and permission, and Guard checks session and permission before construction, so unauthorised requests never reach application code.
298		This ordering makes the safe path the default: one forgotten controller check cannot become a vulnerability, and CSRF is verified once rather than in twenty forms.
299	3	3.4 Technology choices
300		PHP 8.0 ships with XAMPP on the laboratory machines, is well documented and typed strongly enough for this project. MariaDB 10.4 provides InnoDB keys, transactions and the aggregation marking needs. No framework or Composer package is used: a framework would add installation risk and hide the mechanics the assignment assesses, while the custom router and guard are small enough to audit completely.
301		The front end uses semantic HTML and one stylesheet with print rules, keeping the system usable on low-end devices and producing letters and grade sheets without a PDF library. router.php blocks direct access to application, configuration and storage folders under the built-in server; .htaccess does the same under Apache.
302	3	3.5 Deployment and operations
303		Figure 3 shows deployment. The client is a laboratory browser. The application host runs Apache or the built-in server, with uploads and logs in a storage directory that is never served, and MariaDB on the same host over localhost. Mail is written to a log file offline, with an SMTP adapter available. send_mail_queue.php delivers due messages and remind_logbooks.php creates weekly reminders; both can be scheduled with Task Scheduler.
304		
305		Figure 3: Deployment view for the offline laboratory
306		Configuration stays out of source control. The repository ships config.sample.php; config.php is created on first run. Credentials, base URL, debug mode and absolute session lifetime are read from it. Values a coordinator may change — mark weights, due day, lockout thresholds and mail mode — live in the setting table and are edited through a validated screen, so a weight change needs no deployment.
307	3	3.6 Trade-offs and extensibility
308		Server-rendered pages reload more often than a single-page application, but on low bandwidth each page is small, cacheable and works without JavaScript. The custom core costs more code than a framework but removes supply-chain risk and makes security visible. A new capability is a permission row plus a route permission; a new report is a controller method plus a view. Because evidence, assessment and publication are separate, a second instrument needs criterion rows, not a redesign.

310	2	4. Part D — Security and Access Control
311		The system holds student records, workplace assessments and grades. A breach would expose personal data and could invalidate results, so the model assumes an untrusted network, users who probe URLs belonging to others, and administrators who make mistakes. Controls are layered so no single failure grants access.
312	3	4.1 Threat model
313		Assets are credentials, personal data, evidence, scores and marks. Actors are the six roles, an anonymous visitor and a careless or malicious insider. Threats include credential theft, session hijacking, privilege escalation, insecure direct object references, CSRF, XSS, SQL injection, malicious uploads, error leakage and repudiation. Each maps to a control in Table 7.
314	3	4.2 Authentication and sessions
315		Passwords are hashed with password_hash (bcrypt) and verified with password_verify. Registration, reset, invitation and administrator-created accounts all pass one policy helper: at least eight characters with an uppercase letter, a lowercase letter and a number, with symbols optional and encouraged by a live strength meter. Login errors are generic, revealing neither whether an email exists nor whether an account is suspended. Five failures lock the account for fifteen minutes; the counter and timestamp live in users and the event is audited, and an administrator can unlock it. New accounts receive must_change_password and are redirected to the profile until they choose a new password.
316		Cookies are HttpOnly, SameSite=Lax and Secure under HTTPS. Strict mode rejects uninitialised identifiers, and the identifier is regenerated on login to prevent fixation. Idle timeout is twenty minutes and absolute lifetime eight hours. Logout destroys session and cookie, and every dynamic response carries Cache-Control: no-store with Pragma: no-cache while logout also sends Clear-Site-Data: cache, so the Back button cannot redisplay a dashboard from the browser cache. Reset and invitation tokens are random 256-bit values stored only as SHA-256 hashes, single-use, expiring after one hour and seven days.
317	3	4.3 Authorisation
318		Authorisation has two levels. Each route declares a permission that Guard checks before the controller runs; thirty-six permissions span six roles, and the role screen shows the matrix. Object-level checks scope queries to the user’s own record: a student’s logbook joins student on user_id, a supervisor’s queue joins placement on supervisor_id, a mentor’s reports join on mentor_id. Opening another user’s document, letter or entry returns HTTP 403 and writes a security.access_denied event. Table 6 summarises capabilities.

412	3	4.4 Input, output and upload security
413		All SQL uses PDO prepared statements. Output is escaped through e(), and the content security policy forbids inline script, so injected markup cannot execute. Every POST carries a per-session CSRF token, verified globally and rotated at login. Forms validate length, format, ranges and enumeration membership, and rules such as “end date after start date” and “weights total 100” sit in the service layer.
414		Uploads allow PDF, DOC and DOCX for reports and PDF or images for attachments. Extension, detected MIME type and a five-megabyte limit are checked, the stored name is random and the file lives outside the document root. Downloads are served by a controller that re-checks the requester’s relationship to the document, with Content-Disposition: attachment.
415	3	4.5 Auditability and privacy
416		audit_log is append-only in application code. It records logins, failures, lockouts, denials, user, placement and setting changes, logbook decisions and replies, uploads, evaluations, mark computation, moderation, publication, interface feedback and exports, with actor, entity, IP address, user agent and before/after JSON. The audit viewer renders a field-by-field diff, answering who changed a mark and what it looked like before. The same table supplies the placement timeline. When a supervisor, mentor, coordinator or administrator opens an uploaded document, the document row is stamped with reviewed_by and reviewed_at and a document.reviewed event is written; every list then shows “Reviewed by …” with the reviewer and time, or “Not yet opened”, so the uploader can see whether their evidence has been inspected.
417		Management sees aggregates and programme lists, not logbook narratives; supervisors see only their organisation’s students; mentors only their placements. Error pages are generic while detail goes to the PHP error log. Uploads and configuration are blocked from HTTP access, and the offline default sends no personal data externally.

479	2	5. Part E — Implementation and Role Workflows
480		Implementation follows process order. A student cannot submit a logbook until a placement is active, a supervisor cannot evaluate before the placement exists, and a coordinator cannot publish until every component is complete. Screens centre on the next action, not on tables.
481	3	5.1 Student workflow
482		The student dashboard shows the placement, current week, approved entries and unread notifications. Preferences are a ranked list with move controls that reject duplicates and invalid years. An active placement shows the organisation, supervisor, dates and a printable letter generated from the record, so its reference and dates cannot diverge from the database. The logbook lists each week with status; the form captures dates, hours, activity and learning, and attachments add evidence. The report screen accepts one PDF or Word file, and results appear only after publication.
483	3	5.2 Supervisor and mentor workflow
484		The supervisor queue lists submitted entries for the supervisor’s own placements, oldest first. An entry shows the student’s text and attachments; the supervisor approves or returns it, and a return requires a comment that joins the thread and notifies the student. The supervisor then completes a six-criterion evaluation weighted 15, 25, 20, 15, 10 and 15 per cent out of five. Incomplete forms are refused; a completed form stores the weighted total and status submitted.
485		The mentor sees assigned students and a queue of entries that passed supervisor review, comments, and marks an entry mentor-reviewed, which releases it to the logbook average. The mentor schedules site visits with notes and completes a three-criterion evaluation weighted 40, 35 and 25 per cent out of ten, then assesses the report against four criteria weighted 25, 35, 25 and 15 per cent. Each action writes a notification and an audit event.
486	3	5.3 Coordinator, management and administrator workflow
487		The coordinator console is the operational centre. Applications are reviewed with ranked preferences and CV status. Allocation checks that the student has no placement for the year, that the organisation is active with capacity, and that the supervisor belongs to it. A placement moves through proposed, approved, active, completed or cancelled, each transition audited, and the letter appears once approved. The grades screen shows four components, the weighted total and suggested grade; compute, moderate with a reason and publish, after which recomputation is refused.
488		Management sees active placements, completion rate, students without supervisors, overdue logbooks, marks awaiting publication and grade distribution, with a printable report and CSV exports but no logbook narratives. The administrator manages accounts, invitations, suspensions, unlocks and resets, edits the role matrix, maintains settings, monitors the mail queue and reads the audit trail, resending failed messages or processing the queue.
489	3	5.4 Logbook state machine
490		The logbook is a state machine. A draft is editable. Submitting moves it to submitted and notifies the supervisor and mentor. The supervisor returns it with a comment, making it editable again, or approves it; the mentor then comments and moves it to mentor_reviewed. Only mentor_reviewed entries count towards the average. The coordinator and administrator see history but cannot silently change a student’s text. Status answers where it is; the thread answers how it got there.
491	3	5.5 Assessment and publication
492		Figure 4 shows the marking pipeline. The logbook component is the average of mentor-reviewed weekly scores as a percentage; supervisor and mentor components are their evaluation totals; the report component is the assessed report score. Weights come from the setting table, so a change applies to the next computation but never to a published mark. The total is rounded to two decimals, mapped to the grade scale and cached with component percentages. Moderation records a reason and moderator; publication sets status and timestamp and reveals the result.
493		
494		Figure 4: Mark computation and publication pipeline
495		The seed demonstrates the arithmetic: logbook 75.00, supervisor 79.00, mentor 76.50 and report 76.00, weighted 20, 40, 20 and 20 per cent, gives 77.10, grade B+, “Very good”. The results page, grade sheet and management export read the same cached values.
496	3	5.6 Notifications, mail and usability
497		Notifications are written in the same transaction as the business event and paired with an email_queue row. In log mode Mailer appends to storage/logs/mail.log and marks the row sent; failures retain the error and can be retried, so the system works without a mail server. The layout is responsive, tables collapse into labelled rows, destructive actions confirm through data attributes, forms preserve input, and printable documents have a dedicated stylesheet.
498	3	5.7 Interface, guidance and mobile layout
499		The interface was revised after the role walkthroughs under two constraints: the content security policy forbids inline script and style, so every behaviour lives in one external file and every width is set through the CSS object model; and the system must stay usable on the laboratory’s smallest phones. A headless Chrome audit at 427×952, 390×844, 360×800 and 320×700 compared document.scrollWidth with the viewport on every screen of every role and found no horizontal page overflow. Seven-column tables — evaluations, grade breakdown, results, report files, ranked applications and audit changes — no longer clip their last columns: each cell stacks under a data-label caption and a summary row replaces the footer. Charts inside those cells keep a flexible basis with a minimum, so a bar never collapses, while print sheets keep their own A4 layout.
500		Navigation now gives immediate feedback. A top progress bar starts on any same-origin link click and on form submission, the pressed button gains a spinner and aria-busy, and a pageshow handler clears the state when the Back button restores a page. Because the notification dropdown stops click propagation, the listener runs in the capture phase; without that, dropdown links started no bar. The student dashboard also carries a progress tracker: one card derives six steps — placement, logbook, evaluations, visit, report and publication — from the records already loaded and shows them as done, in progress or upcoming with a percentage, so a student can see what remains without opening each module.
501		Three guidance features complete the interface. Signing in uses a single password control with an eye button and no separate show-password checkbox, beside a live strength meter and one-click demo credentials. A floating Send feedback control opens a dialog that records a rating from one to five, free-text thoughts and suggestions, and the current page; it submits as JSON with a toast and thank-you panel, falls back to an ordinary POST without JavaScript, rejects a rating outside the range with HTTP 422 and lists every entry on the administrator’s feedback screen. Finally, logbook comments form a three-way thread: student, host supervisor and academic mentor can each reply, a reply stores parent_id and returns to a #comment anchor, the other two parties are notified, and a reply banner names the parent author with a Cancel control. A first-time student is offered a five-step tour that can be restarted from the layout at any time.

503	2	6. Part F — Evaluation
504		The evaluation asks whether the artefact meets its five objectives and where it would fail in production, using the test pass, security review and role walkthrough.
505	3	6.1 Against the objectives
506		The schema objective is met: nine data stores, twenty-four normalised tables, keys, constraints and transactions. The process objective is met for the core cycle, with every use case from application to publication routed and Assignment 2 numbering preserved. Security is implemented at the application layer and tested. Outputs — letters, grade sheets, reports and CSV — derive from the same data. Realistic seed data and sixty-one executed cases demonstrate the system end to end.
507	3	6.2 Defects found and corrected
508		The test pass was not a formality; seventeen defects were found and fixed. A printable letter used a javascript: link blocked by the content security policy and now receives a real back URL. A route pointed at a missing controller method and was rewired. Source, configuration and storage folders were downloadable under the built-in server and router.php now blocks them. Two notification paths read unselected names and the joins were corrected. The preference swap collided with uq_app_rank and now uses a temporary rank inside a transaction. The forced password change flag was stored but never enforced and a bootstrap gate now enforces it. Mentors could open the supervisor queue and the coordinator’s all-visits page; explicit role gates now return 403 and audit the attempt. The asset helper omitted the assets segment of the public path, so an Apache subfolder install served every page unstyled until the helper was corrected. The sign-in feedback alert stretched down the whole column as a tall pale panel and now keeps its natural height. Finally, a browser Back button could redisplay the cached dashboard after sign-out; no-store headers, Clear-Site-Data and a pageshow reload close that gap.
509		A second pass, driven by the mobile and interface revision, found six more. At phone widths seven-column tables clipped their last columns and forced the page sideways; they now stack with data-label captions and a summary row. Bar charts inside those stacked cells collapsed to zero width until the track received a flexible basis with a minimum. The host supervisor could read a student thread but had no reply form, so the three-way discussion was missing one party; a supervisor comment route, the shared reply banner and notifications complete it. The seeded CV and both report rows pointed at files that were never shipped, so every sample Download link returned 404 on a fresh import; three valid sample PDFs now ship and their recorded sizes match. Links inside the notification dropdown started no loading bar because the panel stops propagation; the listener moved to the capture phase. And under Apache the CSRF rejection page returned 500 rather than 419 because the non-standard code is rewritten; the gate now sends an explicit status line that both Apache and the built-in server preserve.
510	3	6.3 Limitations
511		It is a strong single-institution prototype, not a national service. There is no multi-tenancy, so a second university needs a separate database or a tenant column. Mail ran in log mode, not live SMTP. Timeouts were reviewed in configuration, not observed for twenty minutes. Reports are uploaded and assessed manually, without plagiarism detection. Keyboard access and semantic markup are present, but WCAG 2.2 was not audited by a specialist. The floating feedback control can overlap the lower-right of long content while scrolling, and printing is optimised for A4 rather than arbitrary paper.
512	3	6.4 Recommendations
513		Four improvements matter most: a read-only auditor role; bulk import of students and placements; an offline logbook draft that synchronises when a connection returns; and automated regression tests around mark calculation and the permission matrix. None requires a redesign.

562	2	8. Digital Public Good Analysis
563		A digital public good is open, inclusive, privacy-respecting and sustainable enough to be reused beyond its project. The Digital Public Goods Alliance assesses nine indicators: SDG relevance, open licence, clear ownership, platform independence, documentation, data extraction, privacy, security and do-no-harm. This section evaluates the system against them.
564	3	8.1 Openness and ownership
565		Code is MIT licensed and the report CC BY 4.0. The schema is plain SQL, there is no proprietary dependency and the front end is standard HTML and CSS. Ownership is stated on the cover and in the licence; the university may reuse the work for teaching with attribution. Without a framework or Composer, the artefact is easy to inspect, fork and adapt.
566	3	8.2 Relevance and inclusion
567		The system supports SDG 4 and SDG 8 by making internships accountable. Offline, low-bandwidth design is an inclusion decision: students need no data plan to submit evidence. The interface uses large touch targets, labelled fields, semantic headings, a responsive layout audited from 320 px upwards, loading and progress feedback, and colour paired with text. English is the university’s working language; Krio and Temne strings could be added without schema changes.
568	3	8.3 Privacy and security
569		Only the personal data needed for placement and assessment is stored; management sees aggregates, and object-level scoping keeps evidence private. Security is tested rather than assumed, and the audit trail supports accountability. The do-no-harm assessment identifies misclassification or unauthorised disclosure of a result as the main risk, so publication is deliberate and audited.
570	3	8.4 Sustainability and data extraction
571		Technical sustainability comes from the small dependency footprint and documented installation; institutional sustainability from local ownership, since the university can run the system on existing XAMPP machines and export placements, grades and audit evidence to CSV without vendor permission. Data extraction is a first-class feature, not an afterthought. Table 9 summarises the assessment and remaining gaps.

637	2	10. Conclusion
638		Digital LEAP now has a database and application matching the Assignment 2 analysis. Twenty-four tables preserve the evidence behind every mark, the three-tier architecture keeps rules in one place, the security model assumes users probe boundaries, and the test pass shows the main workflows working. The artefact is deliberately small and offline-first. Its weaknesses — no multi-tenancy, no live SMTP test, no independent penetration test — are the right next tasks.
639		The most important outcome is traceability. A student can see why an entry was returned; a supervisor sees only their own students; a coordinator can show how 77.10 became a B+; an auditor can reconstruct who changed what. That is what a database-backed internship system is for.
