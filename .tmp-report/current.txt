1. Part A — Introduction and Context
Digital LEAP is Limkokwing University’s internship process: placing students with host organisations, supervising weekly logbooks, assessing performance and publishing results. Assignment 2 modelled it as seven processes (1.0–7.0), twenty-two use cases (UC1–UC22) and nine data stores (D1–D9). Most coordination still relies on spreadsheets, email attachments and paper, so data is duplicated, traceability is weak and evidence cannot be reconstructed when a result is challenged.
This report documents the conversion of that model into a working database and a secure, offline-first web application for students, supervisors, mentors, the LEAP coordinator, management and the administrator. The system stores the placement lifecycle in MariaDB, enforces business rules in PHP and generates placement letters, grade sheets, management reports and CSV extracts.
1.1 Aim and objectives
The aim is a normalised database and architecture that make the process auditable, secure and usable on laboratory hardware. Five objectives follow:
map D1–D9 to a normalised schema with enforced integrity;
implement processes 1.0–7.0 and UC1–UC22 behind role-based access control;
protect personal data through authentication, validation and audit;
replace manual consolidation with printable and exportable outputs;
demonstrate the system with Sierra Leone seed data and a repeatable test pass.
Success is more than screens. A coordinator must trace a published mark to the logbook weeks, both evaluations and the assessed report; a student must see only their own record; and a supervisor must not reach another company’s students. These constraints shaped the schema and the architecture.
1.2 Scope and stakeholders
The scope covers preference submission, allocation, logbook review, site visits, evaluations, report assessment, moderation and publication. Payroll, general human-resource management and social features are excluded. Table 1 summarises the stakeholders whose needs drove the requirements.

2. Part B — Database Design
The database tolerates ambiguity least. A logbook entry, an evaluation score and a published mark are records for the student; if they can be silently overwritten or orphaned, the application has failed however good it looks. Design therefore began with the data model.

2.3 Integrity, transactions and indexes
InnoDB foreign keys restrict deletion where history matters. Unique keys prevent duplicate accounts, preferences for one organisation and placements for a student in a year. Enumerated statuses and check constraints cover scores, weights and capacity; PHP validation repeats them at the boundary.
Placement creation inserts the row, writes the audit event and queues notifications in one transaction. Mark computation reads the logbook average, both evaluations and the report score, then writes the mark and its audit snapshot together. The preference swap uses a temporary rank of zero because uq_app_rank forbids shared ranks.
Indexes follow real queries: foreign-key columns for joins, and composites on placement (student_id, academic_year), logbook_entry (placement_id, week_no), evaluation (placement_id, evaluation_type), notification (user_id, read_at) and audit_log (action, created_at).

3. Part C — Technical Architecture
The application must run offline in a computer laboratory on modest laptops and be handed over to another cohort. That rules out a distributed single-page application and a cloud database, and favours server-rendered pages with a minimal dependency footprint.
3.1 Architectural drivers
Five drivers shaped the architecture: offline operation; low bandwidth, favouring server-rendered HTML; security, requiring one entry point for sessions, CSRF and authorisation; maintainability, requiring a layout a student can learn in a week; and auditability, requiring all state changes to pass through one layer.
3.2 Three-tier structure
Figure 1 shows the three tiers. The presentation tier is HTML5 and CSS rendered by PHP, with one small JavaScript file handling confirmations through data attributes; no inline script or style is allowed, which keeps the content security policy strict. The application tier holds the front controller, router, controllers, services and views. The data tier is MariaDB with twenty-eight InnoDB tables. Security is cross-cutting.

Figure 1: Three-tier architecture with cross-cutting security
Controllers read input, call services and select a view. Services own rules that must not be duplicated: Guard decides access, Csrf verifies tokens, Upload validates files, Notify writes notifications and mail together, Mailer delivers queued messages, Settings supplies configuration and Audit records changes. Views escape every value through e().
3.3 Request lifecycle
Every request enters index.php, which loads bootstrap: base paths, autoloader, configuration, storage directories, security headers and a hardened session. Bootstrap checks timeouts, rejects POST requests without a valid CSRF token with HTTP 419 sent as an explicit status line, enforces the forced password change gate and dispatches the route. The router resolves “METHOD route” to a controller, method and permission, and Guard checks session and permission before construction, so unauthorised requests never reach application code.
This ordering makes the safe path the default: one forgotten controller check cannot become a vulnerability, and CSRF is verified once rather than in twenty forms.
3.4 Technology choices
PHP 8.0 ships with XAMPP on the laboratory machines, is well documented and typed strongly enough for this project. MariaDB 10.4 provides InnoDB keys, transactions and the aggregation marking needs. No framework or Composer package is used: a framework would add installation risk and hide the mechanics the assignment assesses, while the custom router and guard are small enough to audit completely.
The front end uses semantic HTML and one stylesheet with print rules, keeping the system usable on low-end devices and producing letters and grade sheets without a PDF library. router.php blocks direct access to application, configuration and storage folders under the built-in server; .htaccess does the same under Apache.
3.5 Deployment and operations
Figure 3 shows deployment. The client is a laboratory browser. The application host runs Apache or the built-in server, with uploads and logs in a storage directory that is never served, and MariaDB on the same host over localhost. Mail is written to a log file offline, with an SMTP adapter available. send_mail_queue.php delivers due messages and remind_logbooks.php creates weekly reminders; both can be scheduled with Task Scheduler.

Figure 3: Deployment view for the offline laboratory
Configuration stays out of source control. The repository ships config.sample.php; config.php is created on first run. Credentials, base URL, debug mode and absolute session lifetime are read from it. Values a coordinator may change — mark weights, due day, lockout thresholds and mail mode — live in the setting table and are edited through a validated screen, so a weight change needs no deployment.
3.6 Trade-offs and extensibility
Server-rendered pages reload more often than a single-page application, but on low bandwidth each page is small, cacheable and works without JavaScript. The custom core costs more code than a framework but removes supply-chain risk and makes security visible. A new capability is a permission row plus a route permission; a new report is a controller method plus a view. Because evidence, assessment and publication are separate, a second instrument needs criterion rows, not a redesign.

4. Part D — Security and Access Control
The system holds student records, workplace assessments and grades. A breach would expose personal data and could invalidate results, so the model assumes an untrusted network, users who probe URLs belonging to others, and administrators who make mistakes. Controls are layered so no single failure grants access.
4.1 Threat model
Assets are credentials, personal data, evidence, scores and marks. Actors are the six roles, an anonymous visitor and a careless or malicious insider. Threats include credential theft, session hijacking, privilege escalation, insecure direct object references, CSRF, XSS, SQL injection, malicious uploads, error leakage and repudiation. Each maps to a control in Table 7.
4.2 Authentication and sessions
Passwords are hashed with password_hash (bcrypt) and verified with password_verify. Registration, reset, invitation and administrator-created accounts all pass one policy helper: at least eight characters with an uppercase letter, a lowercase letter and a number, with symbols optional and encouraged by a live strength meter. Login errors are generic, revealing neither whether an email exists nor whether an account is suspended. Five failures lock the account for fifteen minutes; the counter and timestamp live in users and the event is audited, and an administrator can unlock it. New accounts receive must_change_password and are redirected to the profile until they choose a new password.
Cookies are HttpOnly, SameSite=Lax and Secure under HTTPS. Strict mode rejects uninitialised identifiers, and the identifier is regenerated on login to prevent fixation. Idle timeout is twenty minutes and absolute lifetime eight hours. Logout destroys session and cookie, and every dynamic response carries Cache-Control: no-store with Pragma: no-cache while logout also sends Clear-Site-Data: cache, so the Back button cannot redisplay a dashboard from the browser cache. Reset and invitation tokens are random 256-bit values stored only as SHA-256 hashes, single-use, expiring after one hour and seven days.
4.3 Authorisation
Authorisation has two levels. Each route declares a permission that Guard checks before the controller runs; thirty-eight permissions span six roles, and the role screen shows the matrix. Object-level checks scope queries to the user’s own record: a student’s logbook joins student on user_id, a supervisor’s queue joins placement on supervisor_id, a mentor’s reports join on mentor_id. Opening another user’s document, letter or entry returns HTTP 403 and writes a security.access_denied event. Table 6 summarises capabilities.

4.4 Input, output and upload security
All SQL uses PDO prepared statements. Output is escaped through e(), and the content security policy forbids inline script, so injected markup cannot execute. Every POST carries a per-session CSRF token, verified globally and rotated at login. Forms validate length, format, ranges and enumeration membership, and rules such as “end date after start date” and “weights total 100” sit in the service layer.
Uploads allow PDF, DOC and DOCX for reports and PDF or images for attachments. Extension, detected MIME type and a five-megabyte limit are checked, the stored name is random and the file lives outside the document root. Downloads are served by a controller that re-checks the requester’s relationship to the document, with Content-Disposition: attachment.
4.5 Auditability and privacy
audit_log is append-only in application code. It records logins, failures, lockouts, denials, user, placement and setting changes, logbook decisions and replies, uploads, evaluations, mark computation, moderation, publication, interface feedback and exports, with actor, entity, IP address, user agent and before/after JSON. The audit viewer renders a field-by-field diff, answering who changed a mark and what it looked like before. The same table supplies the placement timeline. When a supervisor, mentor, coordinator or administrator opens an uploaded document, the document row is stamped with reviewed_by and reviewed_at and a document.reviewed event is written; every list then shows “Reviewed by …” with the reviewer and time, or “Not yet opened”, so the uploader can see whether their evidence has been inspected.
Management sees aggregates and programme lists, not logbook narratives; supervisors see only their organisation’s students; mentors only their placements. Error pages are generic while detail goes to the PHP error log. Uploads and configuration are blocked from HTTP access, and the offline default sends no personal data externally.

5. Part E — Implementation and Role Workflows
Implementation follows process order. A student cannot submit a logbook until a placement is active, a supervisor cannot evaluate before the placement exists, and a coordinator cannot publish until every component is complete. Screens centre on the next action, not on tables.
5.1 Student workflow
The student dashboard shows the placement, current week, approved entries and unread notifications. Preferences are a ranked list with move controls that reject duplicates and invalid years. An active placement shows the organisation, supervisor, dates and a printable letter generated from the record, so its reference and dates cannot diverge from the database. The logbook lists each week with status; the form captures dates, hours, activity and learning, and attachments add evidence. The report screen accepts one PDF or Word file, and results appear only after publication.
5.2 Supervisor and mentor workflow
The supervisor queue lists submitted entries for the supervisor’s own placements, oldest first. An entry shows the student’s text and attachments; the supervisor approves or returns it, and a return requires a comment that joins the thread and notifies the student. The supervisor then completes a six-criterion evaluation weighted 15, 25, 20, 15, 10 and 15 per cent out of five. Incomplete forms are refused; a completed form stores the weighted total and status submitted.
The mentor sees assigned students and a queue of entries that passed supervisor review, comments, and marks an entry mentor-reviewed, which releases it to the logbook average. The mentor schedules site visits with notes and completes a three-criterion evaluation weighted 40, 35 and 25 per cent out of ten, then assesses the report against four criteria weighted 25, 35, 25 and 15 per cent. Each action writes a notification and an audit event.
5.3 Coordinator, management and administrator workflow
The coordinator console is the operational centre. Applications are reviewed with ranked preferences and CV status. Allocation checks that the student has no placement for the year, that the organisation is active with capacity, and that the supervisor belongs to it. A placement moves through proposed, approved, active, completed or cancelled, each transition audited, and the letter appears once approved. The grades screen shows four components, the weighted total and suggested grade; compute, moderate with a reason and publish, after which recomputation is refused.
Management sees active placements, completion rate, students without supervisors, overdue logbooks, marks awaiting publication and grade distribution, with a printable report and CSV exports but no logbook narratives. The administrator manages accounts, invitations, suspensions, unlocks and resets, edits the role matrix, maintains settings, monitors the mail queue and reads the audit trail, resending failed messages or processing the queue.
5.4 Logbook state machine
The logbook is a state machine. A draft is editable. Submitting moves it to submitted and notifies the supervisor and mentor. The supervisor returns it with a comment, making it editable again, or approves it; the mentor then comments and moves it to mentor_reviewed. Only mentor_reviewed entries count towards the average. The coordinator and administrator see history but cannot silently change a student’s text. Status answers where it is; the thread answers how it got there.
5.5 Assessment and publication
Figure 4 shows the marking pipeline. The logbook component is the average of mentor-reviewed weekly scores as a percentage; supervisor and mentor components are their evaluation totals; the report component is the assessed report score. Weights come from the setting table, so a change applies to the next computation but never to a published mark. The total is rounded to two decimals, mapped to the grade scale and cached with component percentages. Moderation records a reason and moderator; publication sets status and timestamp and reveals the result.

Figure 4: Mark computation and publication pipeline
The seed demonstrates the arithmetic: logbook 75.00, supervisor 79.00, mentor 76.50 and report 76.00, weighted 20, 40, 20 and 20 per cent, gives 77.10, grade B+, “Very good”. The results page, grade sheet and management export read the same cached values.
5.6 Notifications, mail and usability
Notifications are written in the same transaction as the business event and paired with an email_queue row. In log mode Mailer appends to storage/logs/mail.log and marks the row sent; failures retain the error and can be retried, so the system works without a mail server. The layout is responsive, tables collapse into labelled rows, destructive actions confirm through data attributes, forms preserve input, and printable documents have a dedicated stylesheet.
5.7 Interface, guidance and mobile layout
The interface was revised after the role walkthroughs under two constraints: the content security policy forbids inline script and style, so every behaviour lives in one external file and every width is set through the CSS object model; and the system must stay usable on the laboratory’s smallest phones. A headless Chrome audit at 427×952, 390×844, 360×800 and 320×700 compared document.scrollWidth with the viewport on every screen of every role and found no horizontal page overflow. The fifth pass repeated the audit at 279 px in the application’s embedded browser. Seven-column tables — evaluations, grade breakdown, results, report files, ranked applications and audit changes — no longer clip their last columns: each cell stacks under a data-label caption and a summary row replaces the footer. Charts inside those cells keep a flexible basis with a minimum, so a bar never collapses, while print sheets keep their own A4 layout.
Navigation now gives immediate feedback. A top progress bar starts on any same-origin link click and on form submission, the pressed button gains a spinner and aria-busy, and a pageshow handler clears the state when the Back button restores a page. Because the notification dropdown stops click propagation, the listener runs in the capture phase; without that, dropdown links started no bar. The student dashboard also carries a progress tracker: one card derives six steps — placement, logbook, evaluations, visit, report and publication — from the records already loaded and shows them as done, in progress or upcoming with a percentage, so a student can see what remains without opening each module.
Three guidance features complete the interface. Signing in uses a single password control with an eye button and no separate show-password checkbox, beside a live strength meter and one-click demo credentials. A floating Send feedback control opens a dialog that records a rating from one to five, free-text thoughts and suggestions, and the current page; it submits as JSON with a toast and thank-you panel, falls back to an ordinary POST without JavaScript, rejects a rating outside the range with HTTP 422 and lists every entry on the administrator’s feedback screen. Finally, logbook comments form a three-way thread: student, host supervisor and academic mentor can each reply, a reply stores parent_id and returns to a #comment anchor, the other two parties are notified, and a reply banner names the parent author with a Cancel control. A first-time student is offered a five-step tour that can be restarted from the layout at any time.
5.8 Placement messaging
A supervision question asked by email is lost to the placement record, so messaging is attached to the placement rather than to a private inbox. Four tables — conversation, conversation_member, message and message_reaction — carry the thread, its members and their read positions. Membership is decided by the service, not by the form: a student can reach only the assigned mentor and the coordinator, a mentor reaches the students they supervise and the coordinator, and a crafted start request naming another student returns HTTP 403 and writes a message.denied event.
The thread behaves like a familiar messenger without becoming a social network. A reply stores parent_message_id and renders the quoted parent above the new text; reactions are limited to five emoji; unread counts derive from conversation_member.last_read_message_id and appear in the navigation. A sender may edit a text message for fifteen minutes, after which the control disappears and the server refuses the change; deletion writes deleted_at and leaves a tombstone so replies keep their anchor. A client_token makes a retried send idempotent, attachments pass through Upload::store against the placement, and the open thread polls every eight seconds while the tab is visible. Every messaging table is utf8mb4, so emoji survive the round trip.
Messaging never bypasses the record: message.sent, message.edited, message.deleted and message.denied join the audit trail. The host supervisor keeps the three-way logbook discussion in logbook_comment and has no messaging permission, so the placement conversation stays between the student, the mentor and the coordinator.
5.9 DIVA assistant
Students and staff need a policy answer while they are filling a form, which is when leaving the system is most disruptive. DIVA, the Digital Internship Virtual Assistant, answers from two sources only: the records the signed-in account may already read, and an offline text extract of the internship guidebook in storage/knowledge/guidebook.txt. It makes no cloud call, carries no key and sends no question to an outside service. An optional third tier calls a model on 127.0.0.1 or localhost, is disabled by default and is abandoned after 400 ms, so an unavailable model cannot delay an answer; every reply names the tier that produced it.
Intent rules run first: a deadline, a weighting, a queue or a progress question is answered with a number read from the database, scoped by role, and linked to the page that acts on it. If no rule applies, a ranked search over the 25-page extract returns the strongest passages with page citations, and a source page opens inside the application without losing the question. The report checker reads a .docx with ZipArchive or pasted text, judges the eight Form E criteria against the text, quotes the student’s own line as evidence and runs presentation checks. It never prints a mark and never rewrites a sentence; PDFs are refused with an explanation because the build has no PDF parser. Questions are capped at 500 characters, and each query writes one diva.query audit row with the intent, tier, page numbers and a hash of the question — never its text.
The assistant is read-only by construction: no DIVA route writes, approves, publishes or sends. The twenty-question evaluation set in bin/diva-eval.php exercises all six roles and reports the intent, the answering tier and the cited pages; the recorded run matched both the expected intent and tier twenty times, with eighteen answers from rules and two from guidebook retrieval, while the local tier reported itself disabled on a machine without a model.

6. Part F — Evaluation
The evaluation asks whether the artefact meets its five objectives and where it would fail in production, using the test pass, security review and role walkthrough.
6.1 Against the objectives
The schema objective is met: nine data stores, twenty-eight normalised tables, keys, constraints and transactions. The process objective is met for the core cycle, with every use case from application to publication routed and Assignment 2 numbering preserved. Security is implemented at the application layer and tested. Outputs — letters, grade sheets, reports and CSV — derive from the same data. Realistic seed data and ninety-one executed cases demonstrate the system end to end.
6.2 Defects found and corrected
The test pass was not a formality; defects were found in every pass and each was fixed before the next run; docs/test-log.md numbers them D1 to D26. A printable letter used a javascript: link blocked by the content security policy and now receives a real back URL. A route pointed at a missing controller method and was rewired. Source, configuration and storage folders were downloadable under the built-in server and router.php now blocks them. Two notification paths read unselected names and the joins were corrected. The preference swap collided with uq_app_rank and now uses a temporary rank inside a transaction. The forced password change flag was stored but never enforced and a bootstrap gate now enforces it. Mentors could open the supervisor queue and the coordinator’s all-visits page; explicit role gates now return 403 and audit the attempt. The asset helper omitted the assets segment of the public path, so an Apache subfolder install served every page unstyled until the helper was corrected. The sign-in feedback alert stretched down the whole column as a tall pale panel and now keeps its natural height. Finally, a browser Back button could redisplay the cached dashboard after sign-out; no-store headers, Clear-Site-Data and a pageshow reload close that gap.
A second pass, driven by the mobile and interface revision, found nine more (D12–D20). At phone widths seven-column tables clipped their last columns and forced the page sideways; they now stack with data-label captions and a summary row. Bar charts inside those stacked cells collapsed to zero width until the track received a flexible basis with a minimum. The host supervisor could read a student thread but had no reply form, so the three-way discussion was missing one party; a supervisor comment route, the shared reply banner and notifications complete it. The seeded CV and both report rows pointed at files that were never shipped, so every sample Download link returned 404 on a fresh import; three valid sample PDFs now ship and their recorded sizes match. Links inside the notification dropdown started no loading bar because the panel stops propagation; the listener moved to the capture phase. And under Apache the CSRF rejection page returned 500 rather than 419 because the non-standard code is rewritten; the gate now sends an explicit status line that both Apache and the built-in server preserve. The profile, log book and ranked-list work added three more: the photo preview now runs from a blob URL the image policy allows, asset URLs carry a file version so a change is fetched at once, and the ranked preferences row became a card that keeps its controls with the row.
The final pass, which added the assistant and placement messaging, found six more (D21–D26): an early return in the local tier that made every answer claim a model, an intent order that answered count questions from the wrong rule, a missing logbook-weighting intent, guidebook pages attached to answers that cited none, a citation pattern that lost the second page of a range, and report evidence quoted from the Introduction for every criterion. All six were fixed and re-tested.
6.3 Limitations
It is a strong single-institution prototype, not a national service. There is no multi-tenancy, so a second university needs a separate database or a tenant column. Mail ran in log mode, not live SMTP. Timeouts were reviewed in configuration, not observed for twenty minutes. Reports are uploaded and assessed manually, without plagiarism detection. Keyboard access and semantic markup are present, but WCAG 2.2 was not audited by a specialist. The floating feedback control can overlap the lower-right of long content while scrolling, and printing is optimised for A4 rather than arbitrary paper. Two limits belong to the newest modules. DIVA cannot read PDF text offline, so a report supplied only as PDF must be re-sent as .docx or pasted, and the optional local model was bounded and disabled but never exercised against a running model. Messaging is a placement channel rather than a general inbox: there is no search, no delivery receipt and no thread with anyone outside the placement.
6.4 Recommendations
Four improvements matter most: a read-only auditor role; bulk import of students and placements; an offline logbook draft that synchronises when a connection returns; and automated regression tests around mark calculation and the permission matrix. None requires a redesign.

8. Digital Public Good Analysis
A digital public good is open, inclusive, privacy-respecting and sustainable enough to be reused beyond its project. The Digital Public Goods Alliance assesses nine indicators: SDG relevance, open licence, clear ownership, platform independence, documentation, data extraction, privacy, security and do-no-harm. This section evaluates the system against them.
8.1 Openness and ownership
Code is MIT licensed and the report CC BY 4.0. The schema is plain SQL, there is no proprietary dependency and the front end is standard HTML and CSS. Ownership is stated on the cover and in the licence; the university may reuse the work for teaching with attribution. Without a framework or Composer, the artefact is easy to inspect, fork and adapt.
8.2 Relevance and inclusion
The system supports SDG 4 and SDG 8 by making internships accountable. Offline, low-bandwidth design is an inclusion decision: students need no data plan to submit evidence. The interface uses large touch targets, labelled fields, semantic headings, a responsive layout audited from 320 px upwards, loading and progress feedback, and colour paired with text. English is the university’s working language; Krio and Temne strings could be added without schema changes.
8.3 Privacy and security
Only the personal data needed for placement and assessment is stored; management sees aggregates, and object-level scoping keeps evidence private. Security is tested rather than assumed, and the audit trail supports accountability. The assistant answers only from local records and the offline guidebook, and its audit rows record that it was asked without storing the question. The do-no-harm assessment identifies misclassification or unauthorised disclosure of a result as the main risk, so publication is deliberate and audited.
8.4 Sustainability and data extraction
Technical sustainability comes from the small dependency footprint and documented installation; institutional sustainability from local ownership, since the university can run the system on existing XAMPP machines and export placements, grades and audit evidence to CSV without vendor permission. Data extraction is a first-class feature, not an afterthought. Table 9 summarises the assessment and remaining gaps.

9.2 Maintainability
Routes are declared in one table, controllers are grouped by role, services are single-purpose and views contain no business logic. A new route needs a controller method, a route entry and a navigation link; a new permission needs a permissions row, a mapping and a permission string. The audit trail and test log explain why a rule exists.
9.3 Handover
Handover should be one session: demonstrate the coordinator and supervisor workflows, restore the database, explain the boundary between config.php and the setting table, and walk the audit trail. The new team should run VERIFY.md on a clean machine before changing code. The zip excludes config.php and uploads, so handover must include a database export and an institutional decision on migrating existing evidence.

10. Conclusion
Digital LEAP now has a database and application matching the Assignment 2 analysis. Twenty-eight tables preserve the evidence behind every mark, the three-tier architecture keeps rules in one place, the security model assumes users probe boundaries, and the test pass shows the main workflows working. The artefact is deliberately small and offline-first. A three-tier assistant and placement messaging extend the same record instead of opening a second product. Its weaknesses — no multi-tenancy, no live SMTP test, no independent penetration test — are the right next tasks.
The most important outcome is traceability. A student can see why an entry was returned; a supervisor sees only their own students; a coordinator can show how 77.10 became a B+; an auditor can reconstruct who changed what. That is what a database-backed internship system is for.
